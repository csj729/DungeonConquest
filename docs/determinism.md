# 결정론 코어 — 무엇이고, 왜 그렇게 쓰는가

`CLAUDE.md`의 결정론 규칙이 **왜** 그런지를 담는다. 규칙만 있으면 구현하다 부딪힐
때마다 근거를 다시 유도해야 하고, 그러다 "이 정도는 괜찮겠지"로 새어나간다.

이 문서의 주장은 전부 재현 가능하다 — `tools/determinism_repro/run.sh`

---

## 1. 한 문장

> **같은 시드 + 같은 입력 로그를 넣으면, 어떤 기계에서 몇 번을 돌려도
> 매 틱 `checksum()`이 비트 단위로 같다.**

필요한 이유는 하나뿐이다. **서버가 클라이언트의 런을 재실행해 검증한다.**
클라가 "3맵 클리어, 20분 42초"라고 보고하면 서버는 시드와 입력 로그만 받아
똑같이 다시 돌리고 결과를 대조한다. 한 틱이라도 갈라지면 조작으로 판정된다.

리더보드 신뢰성이 여기에 직결된다. **이 요구가 없으면 C++를 쓸 이유 자체가 없다.**

## 2. 경계 — 무엇이 코어 안이고 밖인가

```
[코어 안]  틱 진행 · 스탯 계산 · 전투 판정 · 스폰 · 확률 · 게이지 · 조합
           ↑ 결정론 규칙 전면 적용
──────────── C ABI (extern "C") ────────────
[코어 밖]  렌더 보간 · 카메라 · 파티클 · 사운드 · UI · 슬로모 연출
           ↑ float 써도 무방. 다음 틱의 상태에 영향이 없다
```

판별 기준은 하나다 — **이 값이 다음 틱의 상태에 영향을 주는가.**

- 히트스톱·배속·일시정지는 **틱을 몇 개 소비할지**만 정한다. 틱 *안의* 계산은
  언제나 고정 속도다. 그래서 2배속으로 돌린 판과 1배속으로 돌린 판의 체크섬이 같다
- 데미지 팝업, 잔상, 화면 흔들림, 에지 마커는 전부 밖이다 (시뮬 상태를 읽어 그리기만 한다)

## 3. 결정론이 성립하는 3요소

| | 내용 |
|---|---|
| **시드** | `World`의 마스터 시드 하나. 모든 확률은 여기서 파생된 스트림 |
| **입력 로그** | `(틱 번호, 종류, 값)` 목록. QTE 판정, 카드 선택 인덱스 — **그게 전부** |
| **고정 순서** | 시스템 실행 순서, 엔티티 순회 순서, 동시 효과 처리 순서 |

**입력이 이렇게 적다는 게 핵심이다.** 한 판 20분에 QTE 수십 회 + 카드 60회 =
수백 바이트다. 서버가 저장하고 재실행하기에 부담이 없다.

일시정지·배속은 **입력이 아니다.** 시뮬을 건드리지 않으므로 로그에 남길 이유가 없다.

## 4. 왜 `float`가 아니라 `Fixed`인가

### 흔한 오해부터

**`float`는 비결정론적이지 않다.** IEEE 754는 `+ - * / sqrt`를 정확히 규정하고,
같은 연산을 같은 순서로 하면 어느 하드웨어에서나 같은 값이 나온다.

문제는 **그 "같은 순서"를 컴파일러가 지켜줄 의무가 없다**는 것이다.

### 메커니즘 1 — FMA 합성 (contraction)

`a*b + c`를 한 명령(`vfmadd132sd`)으로 합치면 중간 반올림이 사라진다.
**C 표준이 이걸 허용한다** — `FP_CONTRACT`의 기본값은 구현 정의다.

같은 소스 · 같은 기계 · 같은 gcc 13.3:

```c
volatile double A = 12052.631484985352, B = 2784.7268676757812, C = -13696.111022949219;
double r = A*B + C;
```

| 플래그 | 결과 비트 | 생성된 명령 |
|---|---|---|
| `-O0` | `417ffed169c856b4` | `vmulsd` + `vaddsd` |
| `-O2 -ffp-contract=off` | `417ffed169c856b4` | `vmulsd` + `vaddsd` |
| `-O2 -mfma -ffp-contract=fast` | **`417ffed169c856b3`** | `vfmadd132sd` |
| `-O3 -march=native` | **`417ffed169c856b3`** | `vfmadd132sd` |
| `-Os` | `417ffed169c856b4` | `vmulsd` + `vaddsd` |

**플래그를 안 주면 gcc 기본값이 `fast`다.** 즉 `-O0`와 `-O2`가 기본 설정에서 갈린다.
그리고 이 기본값은 **컴파일러마다 다르고 버전마다 바뀐다** (GCC / Clang / MSVC).

### 메커니즘 2 — 재결합 (reassociation)

부동소수점 덧셈에는 **결합법칙이 없다.**

```c
volatile double v[4] = {1e16, 1.0, -1e16, 1.0};
double s = 0; for (int i=0;i<4;i++) s += v[i];
```

| 플래그 | 결과 |
|---|---|
| `-O2` | 합 = **1** |
| `-O2 -ffast-math` | 합 = **0** |

`1e16 + 1`은 정밀도가 모자라 1을 삼켜버린다. 순서를 바꿔 `1e16 - 1e16`을 먼저 하면
1이 살아남는다. **`-ffast-math`가 금지인 이유가 이것이고, SIMD 벡터화도 같은 문제다**
(4개씩 묶어 더하면 순서가 바뀐다).

### 메커니즘 3 — x87 초과 정밀도 (32비트 x86)

레지스터가 80비트라 중간값이 더 정밀하고, 메모리로 밀려날 때 64비트로 잘린다.
**언제 밀려나는지는 레지스터 할당이 정하므로 최적화 레벨마다 다르다.**
64비트에선 SSE2를 쓰므로 거의 사라졌지만, 32비트 타깃이 남아 있으면 살아 있다.

### 메커니즘 4 — libm (플래그로 못 막는다)

`sin / cos / tan / exp / log / pow`는 **IEEE 754가 정확도를 규정하지 않는다.**
glibc · musl · MSVC CRT · Apple libm이 서로 1 ulp씩 다르고, 같은 glibc라도 버전이
올라가면 바뀐다. 컴파일 플래그 문제가 아니라 **링크되는 라이브러리 자체가 다르다.**

### 이 프로젝트에서 특히 위험한 이유

코어를 **하나의 바이너리**로 배포하면 전부 통제 가능하다. 그런데 구조가 그게 아니다:

```
같은 소스 ──→ Unity(IL2CPP/Clang)  iOS · Android · Windows · Mac 각각 컴파일
          └─→ 서버(Linux, GCC/Clang)  별도 컴파일
```

**서로 다른 컴파일러 · 다른 플래그 · 다른 libm으로 빌드된 코드가 비트 단위로 같은
결과를 내야 한다.** float로 그걸 하려면 모든 타깃의 백엔드 플래그를 영구히 고정해야
하는데, Unity IL2CPP가 내부적으로 쓰는 최적화 플래그까지 통제할 수는 없다.

## 5. 정수는 정말 안전한가 — 정확한 답

같은 계산을 `Fixed` 20.12로 돌리면:

| 플래그 | `double` | **`Fixed`** |
|---|---|---|
| `-O0` | `...856b4` | `fed157e5` |
| `-O2 -ffp-contract=off` | `...856b4` | `fed157e5` |
| `-O2 -mfma -ffp-contract=fast` | `...856b3` | `fed157e5` |
| `-O3 -march=native` | `...856b3` | `fed157e5` |
| `-Os` | `...856b4` | `fed157e5` |

정수 덧셈·곱셈은 **결합법칙과 교환법칙이 성립**하므로 컴파일러가 순서를 바꿔도
값이 같고, FMA 같은 합성 자체가 존재하지 않는다. §4의 네 메커니즘이 전부 사라진다.

### 하지만 "정수면 끝"은 아니다

**표준이 정확히 규정하는 것** — 컴파일러·버전·플랫폼 무관:

- 부호 없는 정수 `+ - *` (2^N 모듈러 산술)
- 부호 있는 정수 `+ - *` — **오버플로가 없는 한**
- `/` `%` — C++11부터 0방향 절삭으로 규정
- 비트 연산 `& | ^ ~`
- 부호 없는 값의 시프트

#### 잠깐 — UB가 뭔가

**UB = Undefined Behavior (미정의 동작).** C++ 표준이 "이런 코드의 동작은 규정하지
않는다"고 명시한 경우다.

흔한 오해는 "예측 불가능한 값이 나온다"로 읽는 것인데, 실제 의미는 훨씬 세다 —
**컴파일러가 무엇을 해도 표준 위반이 아니다.** 그리고 최적화기는 이 권리를 적극적으로
쓴다: **"UB는 일어나지 않는다"고 가정하고** 코드를 변형한다.

앞의 예가 정확히 그거다. `x + 1 > x`는 수학적으로는 오버플로 시 거짓이 될 수 있지만,
컴파일러는 이렇게 추론한다:

> 부호 있는 오버플로는 UB다 → 프로그래머가 UB를 쓸 리 없다 →
> 오버플로는 일어나지 않는다 → `x + 1 > x`는 **항상 참**이다 → 조건 검사를 지운다

그 결과 값이 틀리는 게 아니라 **루프 종료 조건이 통째로 사라져 무한 루프**가 된다.

표준은 비슷하지만 다른 세 가지를 구분한다:

| 구분 | 뜻 | 결정론 위험도 |
|---|---|---|
| **UB** (미정의) | 표준이 아무 요구도 하지 않음 | **최악** — 같은 컴파일러에서도 최적화 레벨마다 다름 |
| **구현 정의** | 컴파일러가 정하고 **문서화해야** 함 | 중간 — 한 컴파일러 안에서는 일관되지만 **컴파일러 간에는 다를 수 있음** |
| **미명시** | 몇 가지 선택지 중 하나, 문서화 의무 없음 | 중간 — 같은 컴파일러에서도 상황에 따라 다를 수 있음 |

이 구분이 실무에서 갈리는 지점이다. **음수 우측 시프트는 구현 정의**라 주류 컴파일러가
전부 산술 시프트를 하므로 실무상 거의 안전하지만, 표준 보장이 없으니 헬퍼로 격리하고
단위 테스트로 못을 박는다. **부호 있는 오버플로는 UB**라 같은 gcc 안에서도 플래그
하나로 동작이 바뀐다 — 이건 격리가 아니라 **아예 밟지 않아야** 한다.

**UB 또는 구현 정의인 것** — 이게 `CLAUDE.md` 규칙 목록의 정체다:

| # | 함정 | 규격상 지위 | 대응 |
|---|---|---|---|
| 1 | 부호 있는 정수 오버플로 | **UB** | `Fixed` 곱셈은 `int64` 승격 후 시프트 |
| 2 | 음수의 우측 시프트 | C++20 이전 **구현 정의** | `fixed.h` 헬퍼 하나로 격리 + 단위 테스트 |
| 3 | 시프트 폭 ≥ 타입 비트수 | **UB** | 시프트량을 상수로 고정 |
| 4 | `int` / `long` 크기가 플랫폼마다 다름 | 구현 정의 | **`int32_t` 등 고정폭만 사용** |
| 5 | `char`의 부호 | 구현 정의 | 시뮬 상태에 `char` 안 씀 |
| 6 | 부동소수 → 정수 변환에서 범위 밖 | **UB** | 데이터 파일에 정수만 담는다 |

#4가 왜 규칙인지 짚어두면 — Windows는 LLP64라 `long`이 4바이트, Linux/Mac은 LP64라
8바이트다. **같은 소스가 플랫폼마다 다른 범위를 갖는다.**

### UB는 "다르게 동작한다"가 아니라 "무엇이든 한다"

```c
int count(int32_t start){
    int n = 0;
    for (int32_t x = start; x + 1 > x; x++) n++;   /* 부호 있는 오버플로 = UB */
    return n;
}
count(2147483640)
```

| 플래그 | 결과 |
|---|---|
| `-O0` | **무한 루프** |
| `-O2` | **무한 루프** |
| `-O2 -fwrapv` | 7 |

컴파일러는 "부호 있는 오버플로는 일어나지 않는다"고 가정할 권리가 있으므로
`x + 1 > x`를 **항상 참으로 접어버린다.** 값이 달라지는 게 아니라 **코드가 사라진다.**
`-fwrapv`를 주면 7이 나오는 것이 그 가정에 의존했다는 증거다.

`UBSan`은 이걸 실행 시점에 잡는다:

```
runtime error: signed integer overflow: 2000000000 * 2 cannot be represented in type 'int'
```

### 그래서 Debug/Release 체크섬 비교의 정확한 의미

float를 안 쓰므로 부동소수점 차이는 애초에 없다. **그 CI 검사가 실제로 잡는 건 UB다** —
오버플로, 미초기화 값, 스트릭트 앨리어싱 위반. 위 표에서 `-O2`와 `-O2 -fwrapv`가
갈린 게 정확히 그 시나리오이고, `Fixed` 열이 전부 같은 게 "UB가 없으면 최적화 레벨과
무관하다"는 증거다. **UBSan/ASan과 짝을 이루는 그물이다.**

## 6. 코드 레벨에서 깨지는 지점

`Fixed`를 쓰고 UB를 피해도 남는 것들:

- **`std::hash`** — libstdc++와 MSVC가 다른 값을 낸다. 서버-클라 불일치 직행.
  자체 FNV-1a 또는 SplitMix64 finalizer를 쓴다
- **`unordered_map` / `unordered_set` 순회** — 버킷 순서는 삽입 순서와 용량에 의존.
  조회는 안전하지만 순회는 금지
- **포인터 값을 정렬 키나 해시 입력으로** — 주소는 실행마다 다르다 (ASLR)
- **틱 중간 엔티티 삭제** — 인덱스가 밀려 이후 순회가 달라진다. 틱 끝에 일괄 압축
- **동점 처리 누락** — "가장 가까운 적"에서 거리가 같으면? `sourceId` 타이브레이커가
  없으면 순회 순서에 의존한다
- **`std::sort`의 불안정성** — 비교 함수가 완전 순서를 만들면 안전하다.
  동등 원소가 있을 수 있으면 `std::stable_sort`
- **`std::chrono` · 프레임 delta** — 시간은 틱 카운터로만

## 7. 기획 레벨 — 싼 아이디어와 비싼 아이디어

실무에서 제일 중요한 절이다. 기획 단계에서 결정론 비용을 모르면 구현 단계에서
"그건 못 합니다"가 나온다.

**싸다** — 틱·정수로 자연스럽게 떨어진다:
쿨다운 · 지속시간 · 스택 → 틱 카운터 / 확률 발동 → 시드 파생 스트림 /
수치 증감 → `Fixed` / 조건부 효과 → 상태 비교

**비싸다** — 결정론 비용이 붙는다:

| 기획 아이디어 | 왜 비싼가 | 우회 |
|---|---|---|
| "적을 향해 회전한다" | 삼각함수 = libm | 각도 테이블을 데이터로 구움 |
| "반경 R 원형 범위" | 제곱근 | **제곱끼리 비교** (`dx² + dy² ≤ R²`) |
| "포물선 투사체" | 적분 누적 오차 | 고정 틱 스텝 + `Fixed` |
| "넉백으로 밀어낸다" | 위치가 처리 순서에 의존 | 밀림량을 모아 틱 끝에 일괄 적용 |
| "동시에 여러 효과 발동" | 순서가 결과를 바꿈 | **ID 오름차순** 같은 전순서 규칙 |
| "3초 안에 누르면" | 실시간 참조 | 틱 수로 (60틱) |

### 이 프로젝트에서 실제로 결정론 때문에 바꾼 설계들

전부 기획 단계에서 내린 결정이다:

- **훅 실행 순서** — 같은 훅(`onHit` 등)에 여러 효과가 걸리면 **ID 오름차순**으로 고정 (§4)
- **스폰 방향 배분** — 4방향에 균등 배분하고 나머지는 **북 → 동 → 남 → 서 고정 순서**.
  무작위로 돌리면 서버와 클라의 스폰 위치가 갈린다 (§2)
- **몹 체력을 스폰 시점 구간으로 고정** — 구간이 넘어가도 안 바뀐다. 리플레이 시점에
  따라 값이 달라지면 안 되므로 (§2)
- **데이터 파일에 정수만** — JSON 숫자는 부동소수점이라 파서 차이가 곧 불일치 경로.
  `_permille` 등 단위 접미사로 담는다 (`CLAUDE.md`)
- **잠식을 누적 저장값으로** — `corruptionLeft()`는 파생값이라 체크섬에 넣지 않는다 (§10)
- **PRD 연속 실패 카운터를 체크섬 입력에 포함** — 상태를 가진 확률이므로 (§7)

---

## 8. 체크섬 설계

**들어간다** — 저장값:
틱 번호 · 엔티티 배열(위치 · 스탯 raw · 상태) · RNG 스트림 상태 · 잠식 · 클리어 게이지 ·
레벨 · 누적 경험치 · PRD 카운터

**안 들어간다** — 파생값:
캐시된 최종 스탯 · dirty 비트 · `corruptionLeft()` 같은 계산값 · 렌더 전용 데이터

원칙은 **"저장값을 넣고 파생값은 빼라"**다. 파생값을 넣으면 캐시 무효화 타이밍이
체크섬에 새어들어 진짜 버그와 구별되지 않는다.

**시스템별 부분 체크섬**을 따로 기록한다 (Spawn / Combat / Modifier / RNG).
전체 체크섬 하나만 있으면 갈라졌을 때 이진 탐색을 돌려야 하지만, 부분 체크섬이
있으면 "3417틱, Combat에서" 까지 즉시 특정된다.

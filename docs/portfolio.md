# 포트폴리오 어필 포인트

> 이 프로젝트에서 "무엇을 만들었나"가 아니라 **"어떤 문제를 어떻게 풀었나"**를 남기기 위한 문서.
> 기술 나열은 변별력이 없다. 문제 정의 → 접근 → **측정된 결과**의 형태로만 기록한다.

---

## 1. 핵심 메시지

> **결정론 시뮬레이션 코어를 안티치트가 아니라 게임 디자인 도구로 썼다.**

대부분의 프로젝트에서 결정론은 "멀티플레이 동기화" 또는 "치팅 방지"의 수단으로 끝난다.
이 프로젝트는 **하나의 기술 결정에서 세 가지 산출물**을 얻는다:

| 산출물 | 내용 | 수혜자 |
|---|---|---|
| 리플레이 검증 | 서버가 런을 재실행해 결과 검증 | 안티치트 · 리더보드 |
| **몬테카를로 밸런싱** | 헤드리스로 수만 회 시뮬레이션해 밸런스 자동 검증 | 개발 생산성 |
| **분산 부검** | 패배 원인이 빌드 탓인지 운 탓인지 구분해 제시 | 플레이어 경험 |

두 번째와 세 번째가 변별점이다. 결정론이 없으면 둘 다 불가능하다 —
재현이 안 되면 통계를 낼 수 없고, 통계가 없으면 "운이 나빴다"를 증명할 수 없다.

**"측정 후 결정"은 확률뿐 아니라 자료구조 선택에도 같은 방식으로 적용했다** (§4).

## 2. 푼 문제: 확률 게임의 학습 실패

### 문제 정의

가챠·확률 발동 기반 로그라이트에는 구조적 결함이 있다.

1. **분산이 크다.** 스킬 발동 확률, 뽑기 결과, 이벤트 등장이 곱해지면
   같은 스펙·같은 판단에서도 결과 편차가 크다.
2. **플레이어가 잘못 학습한다.** 좋은 판단이 나쁜 결과를 낳았을 때 판단을 바꿔버린다.
   포커·TCG 커뮤니티에서 **결과론(results-oriented thinking)** 이라 부르며 경계하는 오류다.
3. **그래서 피드백을 줄 수 없다.** 실현값 기반 피드백("이번 판 여유 12초")은
   노이즈를 신호로 착각하게 만든다. 그렇다고 피드백을 없애면
   "왜 졌는지 모르는" 뱀서류의 고질병으로 회귀한다.

### 접근 — 세 층으로 분리해서 해결

| 층위 | 문제 | 해결 |
|---|---|---|
| **생성** | 확률 자체의 분산이 과도함 | 의사난수 분포(PRD)로 최악 구간 제거 |
| **노출** | 실현값을 보여주면 결과론 유발 | 실현값 대신 **기대값** 노출 |
| **해석** | 플레이어가 원인을 오판함 | 서버 재시뮬로 **빌드 탓 vs 운 탓** 구분 제시 |

이 세 층 분리가 이 프로젝트 설계의 핵심 논리다.

## 3. 측정된 결과 — PRD 분산 감소

`tools/prd_variance.py`로 시행 200만 회 측정. **기대 발동률은 유지한 채 최악 구간만 잘린다.**

### 발동률 보존 확인

| 목표 발동률 | PRD 상수 C | 실측(순수 난수) | 실측(PRD) | 최대 연속 실패(순수) | 최대 연속 실패(PRD) |
|---:|---:|---:|---:|---:|---:|
| 8% | 0.00955 | 0.0797 | 0.0798 | 149회 | **44회** |
| 12% | 0.02098 | 0.1197 | 0.1197 | 101회 | **30회** |
| 15% | 0.03222 | 0.1497 | 0.1499 | 78회 | **24회** |
| 25% | 0.08474 | 0.2497 | 0.2498 | 46회 | **11회** |

### 연속 실패 K회 이상 발생 확률

| 발동률 | K=10 | K=15 | K=20 | K=30 |
|---:|---:|---:|---:|---:|
| 15% 순수 | 23.2% | 10.3% | 4.57% | 0.87% |
| 15% PRD | 13.8% | 0.89% | **0.014%** | **0%** |
| 감소 배수 | 1.7배 | 11.6배 | **316배** | ∞ |

**해석**: 짧은 연속 실패는 크게 줄지 않지만, **긴 꼬리가 지수적으로 잘린다.**
플레이어가 "억까당했다"고 느끼는 건 K=15 이상 구간이므로, 정확히 그 구간이 제거된다.

### 발견 — 낮은 발동률에서는 PRD가 역효과

측정 중 나온 반직관적 결과:

| 발동률 8% | K=10 | K=20 | K=30 |
|---|---:|---:|---:|
| 순수 | 47.5% | 20.7% | 8.95% |
| PRD | **58.7%** | 11.9% | 0.72% |

발동률 8%에서 K=10 구간은 PRD가 **오히려 더 나쁘다.** PRD는 첫 시행 확률을
C(=0.0096)에서 시작하므로 초반 실패가 순수 난수보다 잦기 때문이다.

**설계 함의**: PRD는 만능이 아니다. 발동률이 낮을수록 효과가 늦게(K=30 이후) 나타나므로,
**발동률을 올리고 계수를 낮추는 쪽(저확률·다시행)이 먼저**다.
25% 구간에서는 K=10부터 137배 감소가 나온다.

> 이 발견 자체가 어필 소재다. "기법을 가져다 썼다"가 아니라
> **"측정해서 적용 한계를 찾아냈다"** 는 증거이기 때문이다.

## 4. 측정된 결과 — 조합식 자료구조 선택

`RecipeData { result, ingredients[] }`(§5) 자체는 데이터 저작 포맷으로 유지하면서,
그 위에 어떤 조회 구조를 얹을지를 **감이 아니라 실측으로 정했다.**

### 문제 정의

"더 좋은 자료구조가 있으면 쓰라"는 요구에 대해, 후보를 나열하고 각각 성능을
주장하는 건 쉽다. 그런데 이 프로젝트는 CLAUDE.md에 이미
**"성능 관련 변경은 추측 말고 측정 후 진행"**이 원칙으로 박혀 있다. 확률(§3)에서
이미 한 번 썼던 태도를 자료구조 선택에도 그대로 적용해야 일관성이 생긴다.

### 측정 방법

`tools/recipe_structure_bench.cpp` (C++, `-O2`, `std::chrono`로 실측). 세 가지 연산을
세 시나리오(현재 규모 51종/42개, 10배 성장 600종/500개 × 재료 ID 무작위/축별 클러스터
두 경우)에서 비교했다.

### 결과

| 연산 | 방식 | 51종/42개 | 600종/500개(무작위) | 600종/500개(클러스터) |
|---|---|---:|---:|---:|
| 아이템→레시피 역조회 | 전수 스캔 | 136 ns | 1453 ns | 1479 ns |
| | 역인덱스 | 17 ns | 18 ns | 17 ns |
| 전체 조합가능 재계산 | 나이브 | 141 ns | 359 ns | 434 ns |
| | 비트마스크 | 85 ns (1.7×) | 470 ns (**0.8×**) | 264 ns (1.6×) |
| 아이템 1개 변경 후 갱신 | 증분 캐시 | 40 ns | 43 ns | 44 ns |

**역인덱스와 증분 캐시는 규모·데이터 형태와 무관하게 항상 이겼다** (역조회 8~85배,
갱신 4~10배). 이 둘을 채택했다.

### 발견 — 비트마스크는 조건부였다

"비트마스크가 빠르다"는 통념과 달리, **재료 ID가 무작위로 흩어져 있으면 비트마스크가
나이브보다 오히려 느렸다** (0.8×). 재료가 2~3개뿐이라 카운트 배열을 직접 2~3번
조회하는 쪽이 이미 저렴한데, 비트마스크는 워드 단위로 훑는 고정 오버헤드가 있어서다.
**아이템 ID를 축(화력·CC·광역·생존)별로 인접하게 배정했을 때만** 1.6~1.9배 이득이 났다.

> PRD가 발동률 8% 이하에서 역효과였던 것(§3)과 같은 패턴이다.
> **"알려진 최적화 기법"은 데이터 형태에 따라 결과가 갈린다** — 이번엔 자료구조 선택에서
> 같은 태도로 같은 종류의 함정을 또 찾아낸 것이다. 우연이 아니라 방법론이 재현된다는
> 증거로 쓸 수 있다.

이 결과로 비트마스크는 채택하지 않았다. 이유가 없어서가 아니라, **측정해보니 이
프로젝트의 재료 수 규모(2~3개)에서는 이득이 없다는 걸 확인하고 뺀 것**이다.

### 채택한 구조 — 기존 아키텍처 원칙의 재사용

```
RecipeData[]  ── 데이터 저작 원본 (변경 없음)
      │ 로드 시 1회 구축
      ▼
역인덱스 (item → recipe[])  ── "이 아이템으로 뭘 만들 수 있지?"
      │ 초기 전수 평가 1회
      ▼
증분 캐시 (recipe별 조합가능 비트)  ── 인벤토리 이벤트마다 영향받는 레시피만 재평가
```

이건 새로 발명한 게 아니라 **§9 모디파이어 시스템의 dirty-flag 패턴을 인벤토리에
그대로 옮긴 것**이다 (design.md §9 "조합식 조회" 참조). "매 틱 전수 평가 금지, 이벤트
기반 무효화"라는 프로젝트 전체 원칙 하나가 서로 다른 두 서브시스템(스탯 모디파이어,
아이템 조합)에서 같은 형태로 재현된다 — **원칙이 일관되게 적용되고 있다는 증거**로
쓸 수 있는 지점이다.

## 5. 어필 자산 체크리스트

포트폴리오에 올릴 때 필요한 산출물. 없으면 주장이 근거 없는 말이 된다.

- [ ] **PRD 분산 비교 그래프** — 위 표를 시각화. `tools/prd_variance.py`가 데이터 생성
- [ ] **몬테카를로 밸런싱 리포트** — 빌드 × 웨이브 조합별 클리어율 히트맵.
      헤드리스 코어를 N만 회 돌려 생성
- [ ] **분산 부검 UI 스크린샷** — "이 빌드의 클리어 확률 70%, 당신은 하위 30%를 뽑았습니다"
- [ ] **CI 밸런스 회귀 로그** — 데이터 변경 시 클리어율이 임계 밖으로 벗어나면 실패하는 파이프라인
- [ ] **Debug/Release 체크섬 일치 CI 로그** — 결정론이 실제로 보장됨을 증명
- [ ] **조합식 자료구조 벤치마크 그래프** — §4 표를 시각화. `tools/recipe_structure_bench.cpp`가
      데이터 생성. "비트마스크가 오히려 느렸던" 막대를 반드시 포함할 것 — 반직관적 결과가
      더 설득력 있다

특히 **몬테카를로 밸런싱**은 인디·소규모 프로젝트에서 거의 볼 수 없다.
대부분 손으로 밸런싱하고 "감으로 맞췄다"고 말한다. 자동화된 밸런스 검증 파이프라인은
그 자체로 강한 차별점이다.

## 6. 서술 템플릿

각 항목을 이 구조로 쓴다. 기술명을 앞세우지 않는다.

```
[문제]  가챠 로그라이트는 확률 분산 때문에 플레이어가 잘못 학습한다.
        좋은 빌드로 운 나쁘게 죽으면 빌드를 탓하게 된다.

[제약]  피드백을 없애면 "왜 졌는지 모르는" 문제로 회귀한다.
        피드백을 주면 노이즈를 신호로 착각한다.

[접근]  생성·노출·해석 세 층으로 분리.
        - 생성: PRD로 연속 실패 꼬리 제거
        - 노출: 실현값 대신 기대값
        - 해석: 결정론 코어로 서버 재시뮬 → 빌드 탓/운 탓 구분

[결과]  발동률 15% 기준, 연속 실패 20회 이상 발생 확률 4.57% → 0.014% (316배 감소).
        기대 발동률은 0.1497 → 0.1499로 보존.
        발동률 8% 이하에서는 PRD 효과가 제한적임을 측정으로 확인하고
        저확률·다시행 구조로 보완.
```

같은 템플릿을 자료구조 선택(§4)에도 그대로 쓴다:

```
[문제]  조합식 조회 구조를 뭘로 할지 여러 후보가 있었다. "더 나은 게 있으면 쓰라"는
        요구였지만, 근거 없이 고르면 그것도 추측이다.

[제약]  이 프로젝트는 이미 "성능은 측정 후 결정"이 원칙이다(CLAUDE.md).
        확률에서만 지킨 원칙이면 일관성이 없다.

[접근]  C++ 벤치마크(-O2, 실측)로 후보 4개(전수 스캔·역인덱스·비트마스크·증분 캐시)를
        3개 시나리오(현재 규모·10배 성장×재료 ID 무작위/클러스터)에서 비교.

[결과]  역인덱스·증분 캐시는 규모·데이터 형태 무관하게 항상 우세 (8~85배, 4~10배).
        비트마스크는 재료 ID가 무작위로 흩어지면 나이브보다 느렸다(0.8×) — 재료 ID를
        축별로 인접 배정했을 때만 이득(1.6~1.9×). 조건부라 채택하지 않음.
        채택한 구조는 §9 모디파이어의 dirty-flag 패턴을 인벤토리에 재사용한 것.
```

## 7. 예상 질문 준비

면접에서 이 주제를 꺼내면 따라올 질문들. 답을 미리 정해둔다.

| 질문 | 준비할 답의 방향 |
|---|---|
| 왜 `float`를 안 썼나요? | 결정론 요구사항. 서버가 클라이언트 런을 **비트 단위로 동일하게** 재현해야 검증이 성립 |
| PRD는 이미 있는 기법 아닌가요? | 맞다. 가치는 적용이 아니라 **적용 한계 측정**에 있다 (8% 역효과 발견) |
| 밸런싱은 어떻게 했나요? | 헤드리스 코어로 몬테카를로. 손 밸런싱이 아니라 분포를 보고 조정 |
| 결정론을 어떻게 보장했나요? | 고정소수점, 고정폭 정수, 컨테이너 순회 금지, UBSan·Debug/Release 체크섬 CI |
| 확률 게임인데 리더보드가 공정한가요? | 주간 고정 시드 → **모든 플레이어가 같은 확률 시퀀스**를 받음. 운이 아니라 판단 경쟁 |
| 왜 비트마스크 안 썼나요? 게임에서 흔히 쓰는 최적화 아닌가요? | 실측하니 재료 ID가 흩어지면 나이브보다 느렸다(0.8×). "흔히 쓰는 기법"도 데이터 형태에 달렸다 — PRD와 같은 교훈 |
| 그 정도 규모(51종)면 어떤 구조를 써도 차이 없지 않나요? | 맞다. 현재 규모에선 전부 서브마이크로초다. 중요한 건 10배 성장 시나리오까지 미리 측정해 **어떤 구조가 스케일에 강한지** 확인한 것 — 나중에 다시 재는 비용을 지금 없앴다 |

마지막 항목은 특히 강하다. 확률 기반 로그라이트에서 공정한 리더보드는
보통 성립하지 않는데, 결정론 코어가 그걸 가능하게 만든다.

## 8. 피해야 할 서술

| 나쁜 예 | 왜 나쁜가 |
|---|---|
| "결정론 시뮬레이션을 구현했습니다" | 기술 나열. 그래서 뭐가 좋아졌는지 없음 |
| "PRD를 적용해 확률을 개선했습니다" | 남의 기법을 가져다 썼다는 말로만 들림. 수치가 없음 |
| "GAS로 아이템 시스템을 만들었습니다" | 엔진 기능 사용 경험. 문제 해결이 아님 |
| "밸런싱에 많은 시간을 들였습니다" | 노력은 성과가 아님 |
| "비트마스크로 최적화했습니다" | 실제로는 채택하지 않았다. 측정해서 **안 쓴 이유**가 더 강한 이야기인데 거꾸로 말하는 꼴 |

**모든 항목에 측정된 숫자를 붙인다.** 숫자가 없으면 그 항목은 빼는 게 낫다.

## 9. 이 문서의 갱신 시점

- PRD 파라미터를 확정할 때 → §3 표 갱신
- 몬테카를로 밸런싱 파이프라인을 만들 때 → §5 체크리스트 해제 + 리포트 첨부
- 분산 부검 UI를 구현할 때 → 스크린샷 확보
- 조합식 조회 구조를 실제 C++ 코어에 구현할 때 → §4를 구현체 기준으로 재확인,
  아이템 종수가 51종에서 늘어나면 벤치마크 재실행

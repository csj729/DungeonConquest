## 1. 프로젝트 개요

- **장르**: 오토배틀러 + 던전 크롤 (오펜스)
- **목표**: Steam 출시. 결정론 시뮬레이션 코어 + 검증 서버 포트폴리오
- **시점**: 쿼터뷰 50~60°, 3D 모델 + **직교 투영** 카메라
- **핵심 기술 주제**: 결정론적 시뮬레이션, 서버 리플레이 검증

### 기술 스택

| 계층 | 기술 |
|---|---|
| 시뮬레이션 코어 | **C++** — static lib, 클라이언트·서버 공유 |
| 클라이언트 프레젠테이션 | **Unity / C# / URP** |
| 서버 | **C# / ASP.NET Core** — 검증 시 C++ 코어를 P/Invoke, MySQL (Linux) |
| 플랫폼 서비스 | Steamworks (업적·클라우드 세이브·리더보드) |

### 언어 선택 기준

**C++는 결정론 코어에만 쓴다.** 언어 선호가 아니라 요구사항이 강제하는 범위까지만이다.

- **코어가 C++인 이유**: 서버와 클라이언트가 **물리적으로 동일한 코드**를 실행해야 한다.
  두 언어로 각각 구현하면 결과 일치를 보장할 수 없고 리플레이 검증이 성립하지 않는다.
  고정소수점 정수 시뮬은 C++의 강점 영역이기도 하다.
- **서버가 C#인 이유**: 리더보드 제출·검증은 사실상 작은 HTTP 엔드포인트다.
  epoll 서버를 직접 구현할 이유가 없다. Unity용으로 만든 **C ABI를 서버가 그대로
  P/Invoke**하므로 시뮬 구현은 여전히 하나뿐이고, 검증 속도도 C++ 코어 그대로다
  (P/Invoke 오버헤드는 틱당이 아니라 런당 1회).
- 네트워킹·DB·툴링은 생산성이 높은 쪽을 고른다. 그 영역까지 C++로 끌고 가지 않는다.

## 2. 게임 구조

플레이어는 전투단을 편성해 던전에 진입하고, 클리어하면 재화를 얻는다.
던전은 여러 조우(encounter)로 구성되며 전투는 전부 자동으로 진행된다.

- 아군이 전진하고, 던전 컨셉에 맞는 몬스터가 이를 저지한다
- 던전 진행 중 **돌발 이벤트** 발생 → 추가 재화 또는 고난
- 전투가 자동이므로 **이벤트가 플레이어의 주요 능동 선택 지점**이다. 부가 요소가 아니라 핵심 시스템으로 설계할 것

### 전력 구성 (비대칭)

| | 구성 | 설계 방침 |
|---|---|---|
| 아군 | 소수 정예 (8종 내외) | 적은 수를 깊게 — 분기 트리, 고유 연출 |
| 적 | 물량 + 소수 엘리트 | 많은 수를 얕게 — 단순 AI, 재사용 변형 |

- 던전마다 **특수 기믹** 존재
- 물량은 스탯(HP 스펀지)이 아니라 **메커니즘**으로 위협할 것
  (우회·포위, 누적 디버프, 특정 아군 마킹, 엘리트에게 버프 공급)

### 이벤트 축

자원 트레이드 / 배치 교란 / 정보 / 육성 기회 / 딜레마

**원칙: 이벤트가 확정된 배치를 흔들 수 있어야 한다.** 배치가 던전 입장 시 잠기기 때문에, 이벤트가 그것을 위협할 때 긴장이 발생한다.

## 3. 배치 — 슬롯 진형

- 진형은 **열(rank)** 로 구성: 전열 / 중열 / 후열
- 각 열에 고정된 개수의 슬롯. 유닛은 슬롯 단위로 배치
- 플레이어의 결정은 "이 유닛을 어느 열에 둘 것인가"로 압축된다
- **배치는 던전 입장 시 1회 확정.** 재배치는 자원 소모나 특정 이벤트 보상으로만 허용

### 슬롯 좌표 — 불변 (확정)

각 슬롯은 **고정된 상대 좌표**를 가진다 (상수).

```
전열: (-60, 0)   (0, 0)   (60, 0)
중열: (-30, 70)  (30, 70)
후열: (-30, 140) (30, 140)
```

수치는 튜닝 단계에서 조정 가능하나 **런타임 중에는 절대 변하지 않는다.**
이 상수성이 오라 사전 계산과 결정론의 근거다.

**동적 진형 변화는 좌표를 바꾸지 않는다.** "전열 전멸 시 중열 자동 전진" 같은 기믹은
**유닛의 슬롯 할당(`unitId → slotIndex`)만 교체**해서 표현한다.

- `AuraTable`은 재계산하지 않는다. 새 `slotIndex`로 재조회할 뿐이다 — O(1)
- 슬롯 할당 변경은 `InAura` 조건의 무효화 트리거다 (5절 참조)

### 진형 이동 (앵커 방식)

- 진형 전체가 하나의 좌표계로 전진
- 각 유닛은 자기 슬롯을 기준으로 교전 반경 안에서만 이동, 적이 없으면 슬롯으로 복귀
- 오라는 **슬롯 기준 상대 좌표**로 계산되므로 이동 중에도 유지된다

### 핵심 긴장 구조

- 시너지 오라 → **뭉칠수록 이득**
- 광역 딜러 엘리트 → **뭉칠수록 손해**
- 던전마다 등장 엘리트가 다르므로 최적 밀집도가 매번 달라진다

**이것이 게임의 핵심 재미 가설이다. 수직 슬라이스에서 1순위로 검증할 것.**

던전 입장 전 등장 몬스터 구성을 공개하여 배치가 정보 기반 판단이 되게 한다.

### 열 개념의 활용

열 인덱스 비교만으로 아래가 전부 표현된다:

- 전열 전용 스킬
- 적 후열 우선 타격 관통형 엘리트
- 전열 전멸 시 중열 자동 전진 (슬롯 할당 교체)
- "후열에 지속 피해" 같은 던전 기믹

## 4. 육성 — 분기형

기본 유닛 종류를 적게 유지하고, 레벨업마다 분기를 선택해 다른 역할로 성장시킨다.
(예: 궁수 → 관통 저격수 / 다중 사격 / 상태이상 살포기)

에셋 물량 대비 빌드 다양성을 극대화하는 것이 목적이다.

### 지속 범위 분리

| 범위 | 내용 |
|---|---|
| **영구** | 캐릭터 해금, 편성 슬롯, 기본 스탯 소폭, 시작 아이템 |
| **런 단위** | 분기 육성 (던전마다 리셋) |

이 분리로 "로스터를 꾸려 나가는" 감각과 재플레이 가치를 동시에 확보하면서, 밸런싱 대상 조합 수를 억제한다.

### 인접 시너지

별도 시스템으로 두지 않고, **특수 캐릭터 또는 육성 분기가 주변에 오라를 부여**하는 형태로 구현한다.

## 5. 모디파이어 시스템

아이템·패시브 스킬·육성 분기·오라는 전부 **모디파이어 컨테이너**다. 별도 시스템을 만들지 않는다.

### 대상 스탯

캐릭터 스펙에 영향을 주는 **모든 스탯**이 대상. 구현 진행하며 필요 시 제외한다.

재계산 시 부수효과가 있는 스탯은 별도 표시하고 전용 핸들러를 거친다:

| 스탯 | 부수효과 |
|---|---|
| `AttackPower`, `Armor` 등 | 없음 — 값만 갱신 |
| `AttackSpeed`, `MoveSpeed` | 진행 중 애니메이션·쿨다운 타이머 처리 필요 |
| `Range` | 타겟팅 캐시 무효화 |
| `AuraRadius` | **모디파이어 대상 아님** (아래 참조) |
| `MaxHealth` | 없음 — 현재 HP를 `damageTaken`으로 저장하므로 부수효과가 발생하지 않는다 (아래 참조) |

### 연산 종류

| 종류 | 동작 | 용도 |
|---|---|---|
| `Flat` | 기본값에 절대 수치 합산 | 장비 기본 옵션 |
| `PercentAdd` | 퍼센트끼리 합산 후 1회 적용 | **기본값** — 대부분의 버프·분기 효과 |
| `PercentMult` | 개별적으로 곱함 | 희귀 아이템, 보스 기믹 등 예외적으로만 |
| `Override` | 최종값 강제 대체 | 속박 등 상태이상 |

`PercentMult`는 지수적으로 폭발하므로 의도적으로 아껴 쓴다. 남발하면 후반 밸런싱이 불가능해진다.

### 적용 순서 (고정)

```
1. Flat        — 누적합           (순서 무관)
2. PercentAdd  — 누적합 후 1회 적용 (순서 무관)
3. PercentMult — sourceId 오름차순 (순서 의존)
4. Override    — sourceId 최소값 하나만 적용, 나머지 무시
```

`Fixed`는 정수이므로 **덧셈에 결합·교환 법칙이 성립한다**(부동소수와 다른 점).
따라서 `Flat` / `PercentAdd`는 정렬이 필요 없고, 순서 고정이 실제로 필요한 것은
`PercentMult`와 `Override`뿐이다.

```cpp
struct StatCache {
    Fixed accumFlat;                     // 추가/제거 시 O(1) 가감
    Fixed accumPctAdd;                   // 추가/제거 시 O(1) 가감
    SmallVec<MultMod, 4>     mults;      // sourceId 오름차순 불변식 유지
    SmallVec<OverrideMod, 2> overrides;  // sourceId 오름차순, front()만 적용
    Fixed cached;
    bool  dirty;
};
```

- 모디파이어 추가/제거는 누적값 가감이므로 **O(1)이고 재계산조차 필요 없다.**
  정수이므로 "제거 시 빼기"가 정확한 역연산이 된다
- `mults` / `overrides`는 원소가 소수(≤4)이므로 **삽입으로 정렬 불변식을 유지**한다.
  재계산마다 정렬 알고리즘을 호출하지 않는다
- `PercentAdd` 누적합이 하한을 넘어가는 경우(예: -100% 이하)는 **스탯별 하한을 데이터로
  정의하고 클램프**한다. 하드코딩 분기 금지
- `sourceId`는 전역 단조 증가 카운터로 발급

### 조건부 모디파이어

허용한다. 아이템·패시브 스킬로 구현.

**이벤트 기반 무효화(dirty flag)** 로 처리한다. 매 틱 전수 평가는 금지.

| 조건 유형 | 재평가 시점 |
|---|---|
| 정적 (`Always`) | 장착/해제 시 1회 |
| 상태 의존 (`HealthThreshold`) | 해당 값 변경 시 |
| 공간 의존 (`InAura`) | **슬롯 할당 변경 / 오라 소스 사망 / 오라 소스 무력화(기절·침묵)** |
| 대상 의존 (`TargetTag`) | 타겟 변경 시 |
| 시간 의존 (`TimeElapsed`) | 해당 틱 1회 |

**`MaxHealth`에 `HealthThreshold` 조건을 거는 것은 금지한다.**
`HealthThreshold` → 현재 HP 참조 → `maxHp - damageTaken` → `maxHp`로 고리가 닫히는
순환 의존이다 (`AuraRadius`를 모디파이어 대상에서 뺀 것과 같은 이유).
`Always` / `InAura` / `TargetTag` / `TimeElapsed` 조건은 `MaxHealth`에도 허용된다.

- 스탯별 dirty 비트 + 캐시된 최종값. 읽을 때 dirty면 재계산 (지연 평가)
- `TimeElapsed`는 전수 스캔하지 않는다. **만료 틱을 키로 하는 최소 힙**으로 관리하고
  동일 틱 타이브레이커는 `sourceId`
- **임계값 조건은 히스테리시스 적용**: 진입/이탈 임계값을 다르게 두어 경계선 진동 방지
  (예: 50% 이하에서 활성, 55% 초과에서 비활성)
- 조건별 현재 활성 비트를 보존해야 히스테리시스 비교가 가능하다

### 오라

- **오라 반경은 고정.** `AuraRadius`는 모디파이어 대상이 아니다 → 순환 의존 원천 차단
- 슬롯 좌표가 상수이므로 **슬롯 간 오라 도달 테이블을 초기화 시 1회 사전 계산**한다
- 전투 중 거리 계산 불필요. 배치 확정 시 대상 유닛의 모디파이어 목록에 삽입하고, 이후 조건 평가만 수행

```cpp
// SLOT_COUNT == 7 이므로 bitset 대신 uint8_t 마스크로 충분하다
struct AuraTable {
    std::array<uint8_t, SLOT_COUNT> reach;   // reach[src] |= (1 << dst)
};
```

### 체력 표현 — 누적 피해량

현재 HP를 직접 저장하지 않는다. **누적 피해량 `damageTaken`을 저장하고 현재 HP는 파생**한다.

```cpp
Fixed damageTaken;                                   // 저장값, 항상 >= 0
Fixed currentHp() const {                            // 파생값
    return max(Fixed::Zero, maxHp() - damageTaken);
}
bool  isDead() const { return maxHp() <= damageTaken; }
```

- 최대 HP가 오르내려도 **손실이 발생하지 않는다.** 현재 HP를 저장하고 클램프하는 방식은
  최대 HP가 내려갔다 올라올 때 클램프된 만큼이 영구 소실된다
- 클램프는 `damageTaken >= 0` 하나뿐이다 (회복 시 오버힐 방지).
  `damageTaken`을 최대 HP로 파괴적으로 클램프하지 않는다 → 조건 토글에 대해 가역적이다
- 체크섬 입력은 파생값이 아니라 저장값 `damageTaken`을 쓴다
- 최대 HP 감소로 `currentHp()`가 0이 되면 사망한다. 이는 버그가 아니라 설계된 결과이며,
  "체력 상한 감소"가 즉사 벡터가 될 수 있음을 밸런싱 시 인지할 것
- 이 표현 덕분에 **`MaxHealth`를 조건부 모디파이어 대상에서 제외할 필요가 없다**
  (단 `HealthThreshold` 조건은 위 순환 의존 때문에 금지)

## 6. 아키텍처

```
        [C++ 결정론 코어]  static lib, 고정 20Hz
          World       틱 카운터, RNG, 엔티티 저장소
          StatBlock   모디파이어 스택, dirty 캐시
          Formation   슬롯 좌표, 오라 테이블
          Targeting / Combat / Movement
                      │
        C ABI (extern "C") — 하나를 양쪽이 재사용
              ┌───────┴────────┐
   SoA 상태 버퍼 + EventQueue   headless run → checksum
   (틱 번호 포함, 단방향)        (렌더·버퍼 없음)
              ▼                ▼
   [Unity 클라이언트]      [C# 서버]  ASP.NET Core, MySQL
    C# / URP                리플레이 검증 · 리더보드
    가변 프레임, 히트스톱,
    카메라, VFX, UI
```

클라이언트용 표면과 서버용 표면은 **같은 ABI의 두 진입점**이다. 코어는 한 번만 구현한다.

### 기반 타입

```cpp
struct Fixed {                      // 16.16
    int32_t raw;
    static constexpr int SHIFT = 16;
};
// 곱셈은 int64_t로 승격 후 시프트
// 시프트·반올림은 헬퍼 하나로 격리 (음수 우측 시프트는 C++20 이전 구현 정의)

struct Rng { uint64_t state; uint32_t next(); };   // xorshift64*
struct EntityId { uint32_t index : 12; uint32_t generation : 20; };
```

- 엔티티는 밀집 배열 + 안정적 인덱스. `generation`으로 삭제 슬롯 재사용 시 오참조 방지
- 전역 RNG 금지. 스트림은 **엔티티별로 파생**한다:

```cpp
uint64_t stream = splitmix64(masterSeed ^ (uint64_t(id.index) << 32) ^ purposeTag);
```

  용도별 스트림 하나를 여러 엔티티가 공유하면 **소비 순서가 결과를 바꾼다.**
  엔티티별 파생은 순서 독립이므로 시스템 순서 변경·병렬화에 강건하고,
  xorshift64\*의 시드 0 문제도 자연히 회피된다.

### 틱 루프

```cpp
void World::tick() {
    ++tickCount;
    drainConditionQueue();  // 전수 평가 아님 — 무효화 큐 + 타이머 힙 소비
    Targeting::run(*this);
    Combat::run(*this);
    Movement::run(*this);
    applyDeaths();          // 틱 끝에 일괄 압축
    swapSnapshots();        // prev ← curr, 렌더 보간용
    flipEventQueue();       // 프레젠테이션이 읽어갈 버퍼로 전환
}
```

### 검증 하네스

**코어보다 먼저 만든다.**

```cpp
uint64_t World::checksum() const;   // 전 엔티티 상태 해시 (자체 FNV-1a — std::hash 금지)
// 같은 시드 N회 실행 → 매 틱 체크섬 일치 확인
// 실패 시 최초로 갈라진 틱 번호 보고
```

- 시스템별 부분 체크섬도 함께 기록 → 갈라진 틱뿐 아니라 **갈라진 시스템**까지 특정
- 임의 틱의 상태 스냅샷을 덤프/로드할 수 있어야 한다. 디버깅 시 diff의 기본 단위다
- Debug/Release 빌드 간 체크섬 일치를 CI에서 검증

## 7. 성능 방침

전력 구성이 비대칭이므로 처리도 비대칭으로 간다.

### 물량 규모 (확정)

| 구분 | 수치 |
|---|---|
| 일반 조우 동시 표시 | **30 ~ 60** |
| 피크 웨이브 (최종 조우, 소환 기믹) | **150 ~ 250** |
| 부하 테스트 목표 | **1024** |
| `MAX_ENTITIES` (고정 할당) | **4096** (`EntityId.index` 12비트) |

투사체는 엔티티가 아니다. 별도 풀로 관리한다.

**상한을 결정하는 것은 GPU가 아니라 판독성이다.** 11절 영구 손실 조건 2("왜 졌는지 읽히는
피드백")가 성립하려면 플레이어가 개별 유닛의 상태 변화를 눈으로 따라갈 수 있어야 한다.
온스크린 500기에서는 불가능하다. 물량은 "메커니즘으로 위협"(2절)하므로 수천이 필요 없다.

**예산 근거**

- 20Hz × 배속 4x = 실시간 80틱/s. 60fps 프레임(16.6ms)당 평균 1.33틱
- 시뮬 예산 프레임당 4ms → 틱당 약 3ms
- N=1024, 균등 그리드 3×3 이웃, 셀당 평균 3기 → 후보 27 → 약 27k회 제곱거리 비교.
  SoA 기준 0.1ms 미만
- **시뮬은 병목이 아니다. 병목은 렌더링과 C++→C# 상태 전달이다**

### 공간 분할

| 계산 | 대상 수 | 방식 |
|---|---|---|
| 아군 간 시너지 오라 | ~8 | 슬롯 테이블 사전 계산 (런타임 계산 없음) |
| 아군 → 적 타겟 탐색 | 8 × N | **브루트포스로 시작** (8×1024는 SoA로 수십 μs. 그리드 간접 참조가 더 비쌀 수 있다 — 측정 후 판단) |
| 적 → 아군 타겟 탐색 | N × 8 | 브루트포스 |
| 적 간 충돌·회피 | N × N | **균등 그리드 필수** |

- 쿼드트리는 불필요. 유닛이 매 틱 움직여 트리 재구축 비용이 더 크다
- 거리 비교는 **제곱 상태로** 수행 (sqrt 호출 제거)

**그리드 구현**: 해시 그리드(`unordered_map`) 금지 — 순회 규칙 위반이고 캐시도 나쁘다.
**밀집 배열 + counting sort**로 매 틱 재구축한다 (동적 할당 0회, O(N), 완전 결정론):

```
1. pass 1: 각 엔티티의 cellIndex 계산 → cellCount[] 증가
2. prefix sum → cellStart[]
3. pass 2: 엔티티 인덱스 순서대로 배치   ← 안정적이므로 결정론 보장
```

- 셀 크기 = 최대 질의 반경 → 3×3 이웃만 조회
- 위치는 SoA (`x[]`, `y[]` 별도 배열)

### 렌더링 (Unity / URP)

| 대상 | 방식 |
|---|---|
| 아군 (8기) | `SkinnedMeshRenderer` — 개별 연출·파츠 |
| 엘리트 | `SkinnedMeshRenderer` |
| 물량 | **VAT (Vertex Animation Texture) + `BatchRendererGroup`** |

- 카메라는 직교 투영(`Camera.orthographic = true`)
- 실시간 그림자 금지 → **블롭 그림자**. 단 URP Decal Projector가 아니라
  **인스턴싱된 quad 메시**로 그린다 (수백 개 규모에서 데칼 프로젝터는 비싸다)
- 오라·사거리 표시는 개수가 적으므로(≤8) URP Decal Projector 사용 가능
- 오클루전 대응: 열마다 Y 오프셋(단차), 가려진 아군 아웃라인
- 후방 물량 LOD, 프러스텀 컬링

### C ABI 경계 (Unity · 서버 공용)

**매 틱 구조체 마샬링 금지.** 이 프로젝트의 유일한 실질적 성능 함정이다.

- C++ 코어가 SoA 상태 버퍼(위치, 회전, 애니 상태, HP 비율)를 **소유**하고 포인터를 반환
- C#는 `NativeArrayUnsafeUtility.ConvertExistingDataToNativeArray`로 **복사 없이** 래핑하여
  `BatchRendererGroup`에 그대로 전달
- 20Hz 시뮬과 가변 프레임 렌더 사이의 보간을 위해 코어가 `prev` / `curr` 두 스냅샷을 유지하고
  C#가 alpha 보간한다. **보간 없이는 60fps에서 눈에 띄게 끊긴다**
- 배속(2x/4x)과 히트스톱은 프레임당 소비할 틱 수와 alpha 계산에만 반영
- `EventQueue`는 POD 배열 + 개수 반환. C#가 틱마다 드레인
- 에디터에서 `[DllImport]`로 로드한 네이티브 DLL은 언로드되지 않아 재컴파일마다 에디터 재시작이
  필요하다. **개발 중에는 수동 `LoadLibrary` / `FreeLibrary` + 함수 포인터 델리게이트 바인딩
  래퍼**를 사용한다
- 빌드: CMake → `core.dll`(Windows) / `libcore.so`(Linux).
  클라이언트는 `Assets/Plugins/<platform>/`, 서버는 런타임 디렉터리에 배치
- **서버 진입점은 별도다.** 상태 버퍼·이벤트 큐 없이
  `run_headless(seed, roster, inputLog) → checksum` 하나만 노출한다.
  P/Invoke 오버헤드는 틱당이 아니라 런당 1회이므로 검증 처리량에 영향이 없다

### 직교 투영을 쓰는 이유

전열과 후열 유닛 크기가 동일해 판독성이 좋고, 슬롯 좌표가 화면 좌표로 선형 매핑된다.

## 8. 서버

싱글 던전 크롤이므로 서버 필요성을 의도적으로 설계한다.

### 주간 고정 시드 던전 + 리플레이 검증 리더보드

1. 매주 전 플레이어에게 동일 시드의 던전 제공
2. 클라이언트가 런 완료 시 **초기 편성 + 시드 + 입력 로그**만 전송 (수 KB)
3. 서버가 동일한 결정론 시뮬레이션을 재실행해 결과 검증
4. 통과한 결과만 랭킹 반영

이 하나로 권위 서버 검증, 안티치트, 리플레이, 리더보드를 동시에 얻는다.
결정론 코어를 서버·클라이언트가 **같은 C++ 바이너리로 공유**하므로 추가 비용이 거의 없다.

### 검증 비용 (7절 물량 상한 기준)

- 1런 = 5조우 × 60초 = 약 6000틱, 평균 N ≈ 200 → 렌더 없이 **0.1 ~ 0.2초/런**
- 주간 제출 10만 건 = 3 ~ 6 코어시. 8코어 30분 내 → **전수 재실행 가능**
- 동시 엔티티가 상시 1000을 넘기면 비용이 약 5배가 되어 계층화 검증
  (체크포인트 체크섬 + 상위권·샘플만 전수 재실행)이 필요해진다.
  7절의 상한은 이 조건도 만족시킨다

### 확장

비동기 PvP (내 편성 스냅샷 vs 상대 편성 자동 전투). 실시간 동기화 불필요.

### 스택

- **C# / ASP.NET Core** (Linux) — 제출 API, 랭킹 조회
- **C++ 코어를 P/Invoke** — `run_headless(seed, roster, inputLog) → checksum` 단일 진입점
- **MySQL** (MySqlConnector)
- **Steamworks** — 업적·클라우드 세이브·리더보드

epoll 서버를 직접 구현하지 않는다. 제출·검증은 작은 HTTP 엔드포인트이고,
이 프로젝트의 기술적 주제는 소켓 처리가 아니라 **결정론 코어의 공유와 재실행 검증**이다.
검증 연산 자체는 C++ 코어가 수행하므로 서버 언어가 검증 성능을 좌우하지 않는다.

## 9. 연출 방침

시청각 액션성은 **점진적으로** 강화한다. 초기에는 최소 연출로 게임 성립을 먼저 확인한다.

- 히트스톱, 카메라 임팩트, 히트 플래시, 데미지 팝업, 처치 연출
- **배속(2x/4x) 기능은 필수**
- 아키텍처는 처음부터 분리해두고 내용물만 나중에 채운다 → 방향 전환 비용 최소화

## 10. 개발 순서

1. `Fixed`, `Rng`, `EntityId` — 기반 타입 + 단위 테스트
   (음수 시프트 · 오버플로 경계 · 나눗셈 반올림 케이스를 반드시 포함)
2. `checksum()` + 재현성 테스트 하네스 + **상태 스냅샷 덤프/로드**
3. `StatBlock` + 모디파이어 (조건 없이 `Always`만)
4. 조건 시스템 + dirty 무효화
5. `Formation` + 오라 테이블
6. Targeting / Combat / Movement
7. **Unity 브리지** — C ABI, SoA 버퍼, `NativeArray` 래핑, prev/curr 보간
8. 물량 부하 테스트 (목표 1024)

**병렬 진행**: Unity에서 프리미티브(캡슐·박스) 프로토타입 + 카메라 각도 슬라이더로 시점 각도 확정.
이 단계는 C++ 코어를 기다리지 않고 더미 데이터로 진행한다.

### 수직 슬라이스 범위

- 던전 1개, 조우 5종
- 기본 유닛 3종 × 분기 3갈래
- 이벤트 8종
- 슬롯 진형 1종

**"한 판이 재미있는가"가 증명되기 전에 콘텐츠를 늘리지 않는다.**

## 11. 미결정

### 손실 지속 범위

던전 간 유닛 손실을 영구 사망으로 할지, 부상/회복 기간으로 할지.

자동 전투에서 영구 손실은 "게임이 부당했다"는 인상을 주기 쉽다. 아래 세 조건이 갖춰지면 영구 손실도 감당 가능하다:

1. 던전 입장 전 적 구성·기믹 정보가 충분히 공개될 것
2. 전투 후 "왜 졌는지" 읽히는 피드백
3. 랜덤이 결과를 뒤집지 않을 것 (랜덤은 상황을 만들되 결과를 결정하지 않는다)

**수직 슬라이스에서 위 셋을 검증한 후 결정한다.**

### 카메라 각도

50~60° 범위. Unity 프리미티브 프로토타입에서 물량을 뿌린 상태로 실측해 확정한다.
확인 기준: 열이 구분되는가 / 아군이 물량에 묻히지 않는가.
